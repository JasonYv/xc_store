# 群机器人「发图」按需截图 — 设计文档

- 日期：2026-07-23
- 范围：跨两个仓库 —— `xc_store`（服务端）+ `pinduoduo_mc`（采集端）
- 状态：设计已确认，待写实现计划

## 1. 目标

群成员在企业微信群里发「机器人发图」时，自动让采集端对该群所属商家截图并发回该群。

现状：采集端只在**固定时间窗口**触发截图。本功能增加**按需触发**通道，不改动原有定时逻辑。

## 2. 数据流

```
群里有人发「机器人发图」
   ↓ WorkTool 机器人回调
[服务端] POST /api/public/worktool-callback?token=<secret>
   ↓ 过滤 roomType=群 + textType=文本 + spoken=="机器人发图"
   ↓ 用 groupName 精确匹配 merchant.groupName
   ↓ 写入内存缓存（合并去重），立刻返回 {code:0,message:"success"}
   ⋮ （采集端每 ~30s 轮询）
[采集端] GET /api/public/screenshot-requests
   ↓ 拿到待发图的 [{merchantId, merchantName, groupName}]
   ↓ 按 merchantId 找到 account_data，复用现有单账号截图 → COS → WorkTool 发群
   ↓ 发送成功后 POST /api/public/screenshot-requests  body={groupName}
[服务端] 从缓存移除该条
```

## 3. 外部契约：WorkTool 消息回调

来源：<https://doc.worktool.ymdyes.cn/doc-861677>、<https://doc.worktool.ymdyes.cn/api-22587884>

WorkTool → 我们的回调接口，请求体（`application/json`）：

```json
{
  "spoken": "机器人发图",
  "rawSpoken": "机器人发图",
  "receivedName": "张三",
  "groupName": "测试群1",
  "groupRemark": "测试群1备注名",
  "roomType": 1,
  "atMe": "false",
  "textType": 1
}
```

字段取值：

- `roomType`：`1`=外部群，`2`=外部联系人（私聊），`3`=内部群，`4`=内部联系人（私聊）
- `textType`：`0`=未知，`1`=文本，`2`=图片，`3`=语音，`5`=视频，`7`=小程序，`8`=链接，`9`=文件，`13`=合并记录，`15`=带回复文本
- 回调接口**必须**返回 `{ "code": 0, "message": "success" }`
- **不支持在响应体内直接下发发送指令**；如需回复须异步调用发送接口。这正契合本设计（服务端只记录，采集端异步发图）。

## 4. 服务端（xc_store）改动

### 4.1 内存缓存模块 `src/lib/screenshot-request-cache.ts`（新增）

- 单例 `Map<string, ScreenshotRequest>`，**key = groupName**。
- 挂在 `globalThis.__screenshotRequestCache__` 上，避免 Next.js dev 热重载丢失；生产 `pm2 instances:1 exec_mode:fork` 单进程，天然单例。

```ts
type RequestStatus = 'pending' | 'processing';
interface ScreenshotRequest {
  merchantId: string;      // merchant.id（采集端 account_data.api_id）
  merchantName: string;    // merchant.name
  groupName: string;       // merchant.groupName
  status: RequestStatus;
  requestedAt: number;     // 首次入队时间戳(ms)
  updatedAt: number;       // 最近一次更新时间戳(ms)
}
```

导出函数：

- `enqueue(merchant)`：同群已存在（pending 或 processing）→ 只刷新 `updatedAt`（**合并去重**，不重复入队）；否则以 `pending` 入队。
- `claimPending(): ScreenshotRequest[]`：`sweep()` 后，取所有 `pending`，标记为 `processing` 并刷新 `updatedAt`，返回列表。
- `complete(groupName)`：从 Map 删除该条（采集端回报成功）。
- `sweep()`（每次读写前内部调用）：
  - `processing` 且 `now - updatedAt > PROCESSING_TTL(5min)` → 退回 `pending`（采集端崩溃/失败没回报时的兜底重试）。
  - `pending` 且 `now - requestedAt > REQUEST_TTL(10min)` → 删除（长期没人取，作废，防堆积）。
- （可选）`list()`：仅调试用，返回快照。

> 时间常量集中在模块顶部：`PROCESSING_TTL = 5*60*1000`、`REQUEST_TTL = 10*60*1000`、轮询侧 30s。

### 4.2 回调接口 `src/pages/api/public/worktool-callback.ts`（新增）

- 方法：`POST`，非 POST 返回 405。
- **鉴权**：URL 携带 secret token —— `?token=<secret>`，与 `process.env.WORKTOOL_CALLBACK_TOKEN` 比对（配置在 `ecosystem.config.js` 的 `env`，与现有 `API_KEY` 同一放法）。不匹配返回 401。
  - 原因：WorkTool 回调不会带我们的 `x-api-key`，无法复用现有 API Key 范式；用 URL token 防止他人伪造请求乱触发发图。
- **过滤**（任一不满足则静默返回 `{code:0,message:"success"}` 并忽略，不报错）：
  - `roomType ∈ {1, 3}`（外部群 / 内部群）
  - `textType === 1`（文本）
  - `String(spoken).trim() === '机器人发图'`（精确匹配）
- **匹配商家**：`await db.init()` 后 `db.getAllMerchants()`，找 `merchant.groupName === body.groupName`。
  - 找不到 → `logger`/`console.warn` 记录群名，返回 `{code:0}` 忽略。
  - 命中 → `enqueue(merchant)`。
- **始终**返回 `{ code: 0, message: 'success' }`（WorkTool 要求；即使忽略也返回成功，避免 WorkTool 重试）。

### 4.3 轮询 + 回报接口 `src/pages/api/public/screenshot-requests.ts`（新增，一个文件两方法）

- 鉴权：现有 public 范式 —— `req.headers['x-api-key'] || req.query.apiKey`，与 `db.getSetting('apiKey')` 比对，不符返回 401。
- `GET`：返回 `claimPending()` 结果。
  ```json
  { "success": true, "data": [ { "merchantId": "xxx", "merchantName": "商家A", "groupName": "测试群1" } ], "total": 1 }
  ```
- `POST`：body `{ "groupName": "测试群1" }`（采集端回报发送成功）。校验 `groupName` 非空，调用 `complete(groupName)`，返回 `{ success: true }`。缺 `groupName` 返回 400。

## 5. 采集端（pinduoduo_mc）改动

### 5.1 接口常量 `app/api_config.py`

`ApiEndpoints` 增加：

```python
# 按需发图（群里发「机器人发图」触发）
SCREENSHOT_REQUESTS = "/api/public/screenshot-requests"   # GET 拉取待发图；POST 回报完成
```

### 5.2 按需发图轮询

- **位置**：商家操作线程（`Pinduoduo()` 实例，`app/task/pinduoduo.py`）的主循环内新增一个每 **30s** 的轮询步骤。该线程已持有登录态浏览器上下文、且现有单账号截图发群能力都在这里，复用最自然、不额外开浏览器。
- **不阻塞定时任务**：轮询是轻量 HTTP + 按需截图，插在现有 `while` 循环的分钟级检查之间；单次按需发图用超时包裹（参照现有 `APPOINTMENT_JOB_TIMEOUT` 做法，建议 `ON_DEMAND_JOB_TIMEOUT`，如 180s），单条卡死自动放弃，不拖垮线程。
- **流程**：
  1. `GET SCREENSHOT_REQUESTS`（带 `x-api-key`）拿到待发图列表。
  2. 对每条按 `merchantId` 在已加载账号里找 `account_data`（`account_data["api_id"] == merchantId`）。
     - 找不到对应账号（未加载/未登录）→ 记日志跳过，**不回报**（留给 TTL 兜底或人工排查）。
  3. 复用现有单账号截图路径：`process_page(page, window_idx, account_data, task_type=...)` → 现有 `_handle_today_data_and_screenshots` / 截图 → COS → `send_screenshot_to_group(group_name=account_data["groupName"], ...)`。
     - 具体复用哪个 `task_type` 与截图方法，在实现计划阶段细读 `pinduoduo.py`（2000+ 行截图流程）后确定，架构上就是「现有单账号截图发群能力」。
  4. 发送成功 → `POST SCREENSHOT_REQUESTS` body `{groupName}` 回报完成。
     - 发送失败 → 不回报；服务端 `PROCESSING_TTL` 到点自动退回 pending，下轮重试。

## 6. 边界与错误处理

- 回调 token 错误 → 401，不入队。
- 群名匹配不到商家 → 忽略并记日志（群名与商家 `groupName` 不一致时便于排查）。
- 同群短时间连发「机器人发图」→ 合并为一条，采集端只发一次。
- 采集端崩溃/发送失败没回报 → `PROCESSING_TTL(5min)` 后退回 pending 重试。
- 请求长期无人处理 → `REQUEST_TTL(10min)` 后作废，防内存堆积。
- 服务端进程重启 → 内存缓存清空（已接受的代价；发图请求本就短时效）。
- 采集端未运行 → 请求 10 分钟后作废；群里发「机器人发图」无响应（符合预期，无采集端就无法截图）。

## 7. 安全

- 回调接口用 `WORKTOOL_CALLBACK_TOKEN`（env）鉴权，防伪造触发。
- 轮询/回报接口沿用现有 `db.getSetting('apiKey')` 范式。
- 影响面受限：即便被触发，图也只发到**已匹配商家的真实群**，不会外泄到任意目标。

## 8. 测试与验证

- **服务端**
  - 缓存模块单元测试：入队 / 合并去重 / claim 转 processing / complete 删除 / TTL sweep 退回与作废。
  - 回调接口：token 校验；roomType/textType/spoken 过滤；命中与未命中商家；始终返回 `{code:0}`。
  - 轮询/回报接口：API Key 校验；GET 返回并转 processing；POST 按 groupName 删除；缺参 400。
  - 手工：`curl` 模拟 WorkTool 回调体 → GET 轮询看到 → POST 回报 → 再 GET 为空。
- **采集端**
  - 用测试群配一个商家（`groupName` 对齐），群里发「机器人发图」→ 观察日志：拉到请求 → 截图 → 发群 → 回报。
  - 失败路径：断网/发送失败 → 不回报 → 5min 后重新拉到。
- **端到端**：真实测试群发「机器人发图」，确认图发回该群，且服务端缓存被清空。
