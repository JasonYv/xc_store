# 员工修改密码 —— 设计文档

日期：2026-08-02
状态：待实现

## 1. 背景与目标

仓库作业系统（`/warehouse`）的员工有两种登录方式：**手机号 + 密码** 和 **登录码**（8 位大写字母数字）。
密码目前只能由管理员在后台「员工管理」里改，员工自己改不了——忘了密码就只能找管理员。

**目标**：员工能自助修改登录密码。用登录码进来的免验旧密码（等于找回密码），
用手机号密码进来的必须验旧密码。

**非目标**：
- 不做短信验证码、邮箱找回
- 不改管理员后台的员工管理功能
- 不动 `/dashboard` 那套管理员认证

## 2. 现状

| 项 | 位置 |
|---|---|
| 员工端登录页 | `src/pages/warehouse/index.tsx`（手机号/登录码两个 tab） |
| 员工端主页面 | `src/pages/warehouse/app.tsx`（底部有「退出登录」按钮） |
| 登录接口 | `src/pages/api/public/employee-login.ts` |
| 注册接口 | `src/pages/api/public/employee-register.ts`（新接口照它的写法） |
| 按手机号校验 | `db.validateEmployeeByPhone(phone, password)` |
| 按登录码查询 | `db.getEmployeeByLoginCode(loginCode)` |
| 密码哈希 | `db.hashEmployeePassword(password)`（SHA-256） |
| 登录码生成 | `generateRandomLoginCode()`（`src/lib/pinyin.ts`） |
| 登录码唯一约束 | `employees.loginCode TEXT NOT NULL UNIQUE` |

员工端登录后把 employee 对象（**含 loginCode**）存在本地，所以换码后能直接显示给员工看，
不需要管理员转达。

## 3. 接口

### `POST /api/public/employee-change-password`

两种入参，对应两种身份来源：

| 场景 | 入参 | 校验 |
|---|---|---|
| 登录码进来 | `{ loginCode, newPassword }` | 登录码存在即可，**免验旧密码** |
| 手机号密码进来 | `{ phone, oldPassword, newPassword }` | `validateEmployeeByPhone` 必须通过 |

两者都传时以 `loginCode` 为准（前端不会这么传，后端按优先级处理避免歧义）。

**成功响应**：

```json
{ "success": true, "data": { "loginCode": "新的8位登录码" } }
```

**失败**：`400` 参数错误 / 密码不合规，`401` 登录码无效或旧密码错误，`500` 服务端异常。
错误信息用中文，与现有接口风格一致。

### 密码规则

**至少 8 位，必须同时包含字母和数字。** 前后端都校验，以后端为准：

```
/^(?=.*[A-Za-z])(?=.*\d)[\S]{8,}$/
```

新密码与旧密码相同时直接拒绝，提示「新密码不能与旧密码相同」。

## 4. 登录码轮换（最容易出事的地方）

改完密码**立即作废旧登录码、生成新的**。这是安全要求，但也意味着：
**员工没记住新码就再也进不来了**。三处防护：

1. **接口返回新登录码**，前端用弹窗强提示，必须点「我已记下」才能关闭
2. **员工端页面常驻显示当前登录码**，改完自动刷新成新值（本地存的 employee 对象要同步更新）
3. **生成时循环查重**：`loginCode` 有 UNIQUE 约束，撞了会插入失败。
   最多重试 10 次，仍冲突则返回 500 并保持密码不变——**宁可改不成，也不能改了密码却没换成码**

**顺序很重要**：先生成不冲突的新码，再在同一次更新里同时写入新密码和新登录码。
不能先改密码再改码——中间失败会导致密码已变、码还是旧的，员工两边都对不上。

现成的 `db.updateEmployee(id, { password, loginCode })` 正好支持一次传两个字段，
内部已经做了登录码查重（撞了抛「登录码已被其他员工使用」）和密码哈希，
**不需要新写数据库方法**。生成新码时先自己查一遍重，把 updateEmployee 的抛错当最后一道防线。

## 5. 前端入口（两处）

### 5.1 员工端内 —— `src/pages/warehouse/app.tsx`

在「退出登录」按钮上方加「修改密码」按钮，点开弹窗：

- 显示当前登录码（方便员工核对）
- 输入新密码、确认新密码
- 因为是登录码身份，**不需要输旧密码**
- 提交后弹出新登录码，必须确认才关闭

### 5.2 登录页 —— `src/pages/warehouse/index.tsx`

在两个登录 tab 下方加「忘记密码？」链接，点开弹窗：

- 输入登录码 + 新密码 + 确认新密码
- 成功后显示新登录码，并提示用新密码或新登录码登录

## 6. 安全权衡（已确认接受）

**登录码等同于最高凭证**：任何人拿到登录码，就能改掉密码并取走新登录码，
原主人会被锁在外面。这是「登录码免验旧密码」的必然结果。

已确认不加额外校验（如手机号后 4 位）。如果将来发现登录码存在外泄风险
（写在纸上、发在群里等），再补一道校验即可，接口预留了扩展空间。

其余安全措施：
- 密码始终哈希存储，接口响应**绝不返回密码字段**（沿用 `Omit<Employee, 'password'>` 的做法）
- 失败信息不区分「登录码不存在」和「旧密码错误」的细节，统一提示，避免被用来探测

## 7. 测试

`xc_store` 目前没有测试框架，按项目现状用**手工测试清单**验证：

| 场景 | 预期 |
|---|---|
| 登录码 + 合规新密码 | 成功，返回新登录码，旧码失效 |
| 登录码不存在 | 401 |
| 手机号 + 正确旧密码 + 新密码 | 成功 |
| 手机号 + 错误旧密码 | 401 |
| 新密码少于 8 位 | 400 |
| 新密码纯数字 / 纯字母 | 400 |
| 新密码与旧密码相同 | 400 |
| 改完用新密码登录 | 成功 |
| 改完用旧登录码登录 | 失败 |
| 改完用新登录码登录 | 成功 |

## 8. 已知风险

1. **员工没记住新登录码就关掉弹窗** —— 只能找管理员在后台查。
   缓解：弹窗强制确认 + 员工端页面常驻显示当前登录码。
2. **并发改密码** —— 同一员工在两个设备同时改，后提交的覆盖前者，
   前者拿到的新登录码已失效。概率极低，不做处理。
3. **登录码空间** —— 36^8 ≈ 2.8 万亿，员工规模下碰撞概率可忽略，
   循环查重已覆盖极端情况。
